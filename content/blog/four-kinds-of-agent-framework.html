When an LLM-based agent becomes part of your architecture, two questions follow: Which framework should you use? And do you need a framework at all?

Depending on who you ask, you might hear names such as DSPy, LangGraph, the Claude Agent SDK, and Amazon Bedrock AgentCore. But these tools belong to different categories, take over different parts of the work, and solve different kinds of problems. Knowing those distinctions will help you choose the right framework, combine several tools, or decide that a small custom implementation is enough.

Start with their common reference point. At its simplest, a tool-using agent is a loop. Call the model, run the tool it asks for, add the result, and go round again. It stops when the task is done or the budget runs out. A tool is any capability the model can ask for by name: one of your functions, a hosted service, an MCP server, or another agent.

Written out, the whole thing is this:

def run(task: str, tools: dict) -> str:
    messages = [{"role": "user", "content": task}]

    for _ in range(MAX_STEPS):
        reply = client.chat.completions.create(
            model="gpt-5",
            messages=messages,
            tools=[schema(t) for t in tools.values()],
        ).choices[0].message
        messages.append(reply)

        if not reply.tool_calls:
            # Nothing left to do.
            return reply.content

        for call in reply.tool_calls:
            # Run the tool it asked for.
            args = json.loads(call.function.arguments)
            tool = tools[call.function.name]
            messages.append({
                "role": "tool",
                "tool_call_id": call.id,
                "content": str(tool(**args)),
            })

    raise RuntimeError("step budget exhausted")

That fits on one screen. Streaming, budgeting, retries and real error handling expand it quickly. Keep it in view. Three of the categories below take a different part of this away from you, and the fourth wraps the whole thing. That is what separates them: which part you keep, and which part you hand over.

These are not layers in a fixed stack. Each names the responsibility a tool mainly takes over, and one system can use several at once.

Feature lists do not tell you which category you need, because these tools overlap and often compose. What sorts them is the responsibility you stop carrying, and that gives the rule: two tools compete only if you would hand them the same responsibility. Comparing DSPy with Mellea is worth doing. Comparing DSPy with LangGraph is a category error.

Generation-level tools

These tools turn a hand-rolled model call into a declared interface. You keep the program and say what a good answer looks like. Each one takes over some combination of prompt construction, parsing, validation, repair and optimization. "One model call" is too narrow a name for the category, because the work does not always happen at runtime.

The failure sits inside a generation step. The model may return the wrong structure, break a requirement you can validate, or vary in quality across examples. More orchestration will not repair the generation itself.

Three approaches, and what separates them is when they act. BAML acts at the boundary, and is a language rather than a framework: you write the prompt inside a typed function, and its compiler generates the client your program imports. Mellea acts at runtime, retrying whatever fails a requirement you attached. DSPy acts before deployment: its optimizer searches with examples and a metric for better instructions, better demonstrations, or both.

BAML, Mellea and DSPy combine, and the cost usually rises in that order. Declaring a type is often straightforward, a reliable validator takes more work, and a scoring function can become a project of its own.

In code, the loop does not move. One tool inside it stops carrying a prompt:

class ExtractInvoice(dspy.Signature):
    """Read an invoice and return what is payable."""

    document: str = dspy.InputField()
    amount: float = dspy.OutputField()
    due_date: str = dspy.OutputField()

extract = dspy.ChainOfThought(ExtractInvoice)

No formatting instructions and no parsing code. The docstring becomes the instruction DSPy sends, and the field types tell it what to coerce the result into. Wrap extract in a plain function and run() calls it like any other tool. What declaring and optimizing looks like in full is its own subject.

One name causes more confusion than the rest. Since 1.0, LangChain is a high-level agent API running on the LangGraph runtime, so it belongs with orchestration rather than here.

Orchestration frameworks

Orchestration frameworks give you the loop: control flow, state, and what happens when a step fails. What they do not hand you is an assembled environment. Some ship hosted tools, sandboxes or workspace execution, but you still choose and wire the capabilities your application needs. A prebuilt harness arrives with that already assembled for a class of tasks. That is the right trade when your tools are three calls into your own API. It becomes the wrong one when you would otherwise assemble repository access, shell execution, sandboxing and permissions yourself.

Two forks decide which one you want, and neither is about the brand.

Either your code picks the next step, or the model does. Strands starts from a model-driven loop. LangGraph starts from an explicit state graph but can mix deterministic and model-driven nodes. CrewAI separates autonomous Crews from structured Flows. This is not merely a matter of taste. If you can draw the flowchart, write the flowchart. Letting the model decide costs tokens and latency, and hides why the agent did what it did.

What does it cost you when a run dies halfway? If the answer is "nothing, we rerun it," retries are fine. If the run takes an hour or waits on an approval, it has to save progress outside the process. That means checkpointing, or a real workflow engine underneath. Pydantic AI takes the second route. That is what I would look at hardest for anything long-running.

In code, the for loop and the message list are gone. You declare the steps and the framework runs them:

graph = StateGraph(State)
graph.add_node(fetch_policy)
graph.add_node(draft_reply)
graph.add_edge(START, "fetch_policy")
graph.add_edge("fetch_policy", "draft_reply")
graph.add_edge("draft_reply", END)

config = {"configurable": {"thread_id": "42"}}
app = graph.compile(checkpointer=InMemorySaver())
app.invoke({"ticket": ticket}, config)

fetch_policy and draft_reply are still your functions, and their tools are still yours to write. What you handed over is range(MAX_STEPS), the growing messages list, and what happens when step two dies. Swap the saver for a database and the run resumes on the same thread_id.

Prebuilt harnesses

The word needs pinning down. Used loosely it means everything around the model, which would make every orchestration framework one. This category is narrower: a prebuilt harness that you invoke from your own code. Where the previous kind hands you the loop empty, this one hands it full. It arrives with file access, a shell and a sandbox, plus the permission gates and session resumption that keep a long run alive.

You are driving an agent, not building one. That is the bargain: you inherit its tools, system prompt, and context strategy. Most of it can be extended or overridden, but you did not write it and you do not maintain it. You keep the task, the permissions, and whatever hooks it exposes.

In code there is no loop left to see, and no tools dictionary either:

options = ClaudeAgentOptions(
    allowed_tools=["Read", "Edit", "Bash"],
    permission_mode="acceptEdits",
    cwd="/srv/checkout",
)

task = "Add the new argument to every render_legacy call."

async for message in query(prompt=task, options=options):
    print(message)

Compare that with the first snippet. You no longer wrote the tools that read and edit files, nor the system prompt that picks between them. What stays yours is the sentence, the three tools you permitted, and the directory it may touch.

Harnesses look alike from outside, and the model you already pay for narrows the list quickly. They differ underneath in sandboxing, permissions, which tools ship, and how much of the loop you can replace. One is worth singling out: the coding agent pi is small enough to read rather than adopt.

That bargain is easiest to judge from the inside, and I have paid what this category charges. Building a generative UI agent for IBM Think 2026, I needed to go from a visitor's idea to a running app in two minutes, live. The agent was Bob, IBM's coding agent, and it had no SDK, so the integration point was bob -p "your prompt" as a subprocess. It supplied the model and the tools. I supplied the task and a deterministic build step around it. The full build is here.

You also inherit somebody else's product roadmap. Google retired Gemini CLI in May 2026 and stopped serving requests on 18 June. That is a fast cycle to be downstream of.

Enterprise agent platforms

What you buy here is the perimeter around the orchestration: which identity the agent acts under, what it may access, what it does, and where the agent runs and its memory lives. Better reasoning is not what this category sells. Platforms do orchestrate, which is why sorting on capability alone would stack them on the previous kind instead of setting them beside it.

The split inside the category matters more than the brand. Business-user surfaces let a domain expert compose the agent, and many large vendors offer one wired into their own data and application ecosystems. Developer runtimes assume you wrote the agent already and need somewhere accountable to run it.

You need this kind when the sentences blocking your launch start with "who approved," "who can see," or "what happens when it is wrong." Those are the loudest signals. Managed deployment, data residency and central governance can bring you here before anyone says them.

Which one do you need?

Reaching for the wrong kind fails predictably. Answer an unreliable extraction step by adding a second agent to check it at runtime, and you have added a second unreliable generation. You now coordinate the pair as well. Start with the provider's structured output or a deterministic validator, then score the step offline against examples. Add runtime verification when it checks something independently or enforces a policy.

A prototype usually needs one kind. Production systems often combine several, and each addition should answer a failure you have seen. The pairing I reach for is orchestration plus a generation-level tool, when the steps are known and one of them has to be accurate.

Should you write your own?

Write that loop yourself the first time. A minimal version is small enough to build as an exercise, and afterwards none of the frameworks look like magic. What it does not buy is production readiness. The trap is durability: a hand-rolled way of saving progress is often worse than none, because it looks like it works until the process dies at the wrong moment.

Keep it hand-written while four things stay true. The output contract is simple enough to enforce yourself. The path is a fixed sequence you can draw. Your tools are a handful of calls into your own API. Nobody outside your team approves what it does. When one of those stops being true, it names the responsibility to hand over next.

You will still get a choice wrong, so prefer tools that speak the standard protocols: MCP to reach a tool, A2A to call another agent, ACP to talk to an editor. Then replacing one costs less, though no protocol erases the differences in state, permissions and error handling.

That leaves the two questions you arrived with. Which framework? Start with the category matching the responsibility your system can no longer carry. Compare inside it on ecosystem fit, extensibility, operational maturity and exit cost. Should you write your own? Yes, once, and keep it until one of those four conditions goes false.

The names on this page will churn, and two were renamed while I was writing it. The responsibilities move far more slowly.
