You are starting a project that needs an LLM-based agent somewhere in the architecture. Two questions arrive together: which framework should I use, and should I write my own instead?

Neither can be answered from the shortlist you are holding. It probably has DSPy, LangGraph, the Claude Agent SDK and Bedrock AgentCore on it, and no two of those four do the same job. You cannot rank a list of things that are not alternatives. Sort it first and both questions get much easier.

They all sit around the same thing, so name it once. An agent is a loop: assemble some context, call the model, run the tool it asks for, add the result, and go round again until the task is done or the budget runs out. A tool is one of your own functions the model may ask for by name.

Written out, the whole thing is this:

def run(task: str, tools: dict) -> str:
    messages = [{"role": "user", "content": task}]

    for _ in range(MAX_STEPS):
        reply = client.chat.completions.create(
            model="gpt-5",
            messages=messages,
            tools=[schema(t) for t in tools.values()],
        ).choices[0].message
        messages.append(reply)

        if not reply.tool_calls:            # nothing left to do
            return reply.content

        for call in reply.tool_calls:       # run what it asked for
            args = json.loads(call.function.arguments)
            messages.append({
                "role": "tool",
                "tool_call_id": call.id,
                "content": str(tools[call.function.name](**args)),
            })

    raise RuntimeError("step budget exhausted")

Twenty lines. Add streaming, retries and a real token budget and it reaches about forty, which is still not the hard part. Keep it on screen, because each category below is a claim about which of these lines stop being yours. What separates the four kinds is which part of it you keep, and which part you hand over.

Comparing capabilities gets you nowhere, because they overlap almost completely. Any of them can call any other, since asking for a tool is a function call and nothing more. What sorts them is what you stop being responsible for, which gives the rule that makes a shortlist tractable: two tools compete only if you would be handing them the same responsibility. DSPy against Mellea is a real decision. DSPy against LangGraph is a category error.

Generation-level tools

What you hand these is the prompt. You keep the program and declare what a good answer looks like. The tool takes over the wording, the parsing, and how many attempts it makes. That last part is why "one model call" is the wrong name for the category: sampling and repair loops fire as many as they need.

The failure is specific: the steps were right, the tools worked, and the model still returned prose where you needed JSON. Control flow above this cannot fix it.

Three approaches, and what separates them is when they act. BAML acts at the boundary, and is a language rather than a framework: prompts become typed functions it compiles into a client you import. Mellea acts at runtime, retrying whatever fails a requirement you attached. DSPy acts before runtime, rewriting the instructions against a scoring function until the score goes up.

They combine, and the entry fee rises in that order. A type is free, a requirement you can check is cheap, and a function that scores an answer is usually the real project.

In code, the loop does not move. One tool inside it stops carrying a prompt:

class ExtractInvoice(dspy.Signature):
    """Read an invoice and return what is payable."""

    document: str = dspy.InputField()
    amount: float = dspy.OutputField()
    due_date: str = dspy.OutputField()

extract = dspy.ChainOfThought(ExtractInvoice)

No wording, no JSON instructions, no parsing. extract goes into the tools dictionary and run() is untouched. What declaring and optimizing looks like in full is its own subject.

One correction to the common map, because it moves a tool between categories: LangChain used to belong here, but since 1.0 it is an agent API on the LangGraph runtime, which makes it an orchestration framework.

Orchestration frameworks

These give you the loop: control flow, state, and what happens when a step fails. They do not give you tools. That is the sharp line between this category and the next. LangGraph ships nothing that can touch your filesystem; Strands ships nothing that can run a shell command. Every capability is one you wrote, which is right when your tools are three calls into your own API and wrong when the agent must work in a repository.

Two forks decide which one you want, and neither is about the brand.

Either your code picks the next step, or the model does. Strands takes the model side, LangGraph the explicit side, and CrewAI ships both. This is not taste. If you can draw the flowchart, write the flowchart: letting the model decide costs tokens and latency, and makes it much harder to work out afterwards why the agent did what it did.

What does it cost you when a run dies halfway? If the answer is "nothing, we rerun it," retries are fine. If the run takes an hour or waits on a human approval, it has to save its progress outside the process. That is either checkpointing or a real workflow engine underneath, which is the route Pydantic AI takes. It is what I would look at hardest for anything long-running.

In code, the for loop and the message list are gone. You declare the steps and the framework runs them:

graph = StateGraph(State)
graph.add_node(fetch_policy)
graph.add_node(draft_reply)
graph.add_edge(START, "fetch_policy")
graph.add_edge("fetch_policy", "draft_reply")
graph.add_edge("draft_reply", END)

app = graph.compile(checkpointer=InMemorySaver())
app.invoke({"ticket": ticket}, {"configurable": {"thread_id": "42"}})

fetch_policy and draft_reply are still your functions, and the tools they call are still yours to write. What you handed over is range(MAX_STEPS), the growing messages list, and what happens when step two dies: swap the saver for a database and the run resumes on the same thread_id.

Language is the next filter, and it deletes most of the list on its own. Nearly everything here is Python first, TypeScript sometimes, and nothing else. One warning about the exception: Google ADK spans four languages, but it is also the front door to Google's runtime, so adopting it quietly picks that too.

Prebuilt harnesses

The word needs pinning down. "Harness" generally means everything around the model, so by that definition every orchestration framework is one. This category is narrower: a harness somebody already built, that you run from your own code. It arrives able to act in a real environment, reading and writing files, running shell commands, working inside a sandbox, and speaking the Model Context Protocol (MCP) to whatever else you connect. It brings what keeps a long session alive too: permission gates, session resume, and summarising the conversation once it outgrows the context window.

Where the previous category hands you the loop empty, this one hands it full. You are driving an agent, not building one, usually as a subprocess on your own machine. What you give up is the inside: the tools, the system prompt and the context strategy are theirs. You keep the task, the permissions, and whatever hooks they expose.

In code there is no loop left to see, and no tools dictionary either:

options = ClaudeAgentOptions(
    allowed_tools=["Read", "Edit", "Bash"],
    permission_mode="acceptEdits",
    cwd="/srv/checkout",
)

async for message in query(
    prompt="Add the new argument to every call site of render_legacy.",
    options=options,
):
    print(message)

Compare that with the first snippet. Reading files, editing them and running the tests are tools you no longer wrote, and neither is the system prompt that decides when to use which. What is left yours is the sentence, the three tools you permitted, and the directory it may touch.

Most of them are the same bargain from a different vendor, so the choice is usually whichever model you already pay for. Two exceptions are worth knowing: pi is small enough to read rather than adopt, and Managed Agents is this category as a service, where the loop and the sandbox are somebody else's machine instead of yours.

I have paid what this category charges. Building a generative UI agent for IBM Think 2026, I needed a coding agent to go from a visitor's idea to a running app inside two minutes, live. The agent was Bob, IBM's, and it had no SDK, so the integration point was bob -p "your prompt" as a subprocess. It supplied the model and the tools; I supplied the task and a deterministic build step around it. The full build is here.

You inherit two things: opinions you did not choose, and a product roadmap. Google retired Gemini CLI in May 2026 and stopped serving requests on 18 June. That is a fast cycle to be downstream of.

Enterprise agent platforms

Platforms orchestrate too, so capability would put them on top of the previous category rather than beside it. What makes them a different purchase is the perimeter wrapped around the orchestration: which identity an agent acted under, credentials handed over without handing over secrets, what it may touch, what it did, and where memory, evaluation and deployment live. What you do not buy is better reasoning.

The split inside the category matters more than the brand. Business-user surfaces let a domain expert compose the agent, usually drag-and-drop with a developer kit underneath, and every large vendor sells one over its own data. Developer runtimes assume you already wrote the agent and need somewhere accountable to run it. They sell runtime, memory, identity and monitoring as separate services, and do not care which framework wrote the agent.

You need this category when the sentences blocking your launch start with "who approved," "who can see," or "what happens when it is wrong." If none of those has been said to you yet, you do not need it.

Which one do you need?

Reaching for the wrong kind fails predictably. Answer an unreliable extraction step with a second agent that double-checks the first, and you have added another unreliable generation plus the job of coordinating the pair. A second pass only helps when the checker looks for something the first step did not.

Combinations worth running

One kind alone is the common case. A classification service is a generation-level tool and your own code. A CI job that fixes failing tests is a harness in a shell script, because the harness already owns the loop.

Two pairings earn a second dependency. Orchestration plus generation-level, when the run has known steps but one of them must be accurate: a document pipeline whose extraction step is a DSPy program. The pairing I reach for goes further and puts a module behind every step, which buys a score per step instead of one for the whole run.

Orchestration plus a harness, when repo work is one step of something larger. A migration across two hundred services needs a queue, restart survival and an approval gate, while reading each repository is harness work invoked per service. Do not invert that one: an orchestrator inside a harness loop, supervising an agent that already supervises itself, buys overhead and nothing else.

Should you write your own?

Write that loop yourself the first time. It is a day of work, and afterwards none of the frameworks look like magic. What it does not buy is production readiness, and the trap is durability: a hand-rolled way of saving progress is often worse than none, because it looks like it works until the process dies at the wrong moment.

Keep it hand-written for as long as four things stay true. The output is easy to check. The path is a fixed sequence you can draw. Your tools are a handful of calls into your own API. Nobody outside your team has to approve what it does. Each of those four going false points at one of the four categories, in that order. You are noticing which responsibility you no longer want.

You will still get one of these wrong. Three protocols now cover the points where the kinds meet: MCP for how an agent reaches a tool, A2A for how one agent calls another across a vendor boundary, and ACP for how an editor talks to a coding agent. Pick tools that speak them and a wrong choice stays a swap.

The framework names on this page will churn. Two of them changed identity while I was writing it. What you can hand over will not.
