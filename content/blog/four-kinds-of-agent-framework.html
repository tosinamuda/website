You are starting a project that needs an LLM-based agent somewhere in the architecture. Almost immediately, two questions arrive together: which framework should I use, and should I just write my own from scratch?

Neither has an answer yet, because the tools on the shortlist are not doing the same job. DSPy, LangGraph, the Claude Agent SDK and Bedrock AgentCore can all be proposed for one project, and picking between them compares nothing.

They all sit around the same thing, so name it once. An agent is a loop: assemble some context, call the model, run the tool it asks for, add the result, and go round again until the task is done or the budget runs out. A tool is one of your own functions the model may ask for by name. That loop is about forty lines, and writing it is not the hard part. What separates the four kinds is which part of it you keep, and which part you hand over.

Comparing capabilities gets you nowhere, because they overlap almost completely. Any of them can call any other, since asking for a tool is just calling a function. What sorts them is what you stop being responsible for, which gives the rule that makes a shortlist tractable: two tools compete only if you would be handing them the same responsibility. DSPy against Mellea is a real decision. DSPy against LangGraph is a category error.

Generation-level tools

What you hand these is the prompt. You keep the program and declare what a good answer looks like; the tool takes over the wording, the parsing, and how many attempts it makes. Note that this is not "one model call," since sampling and repair loops fire several.

The failure is specific: the steps were right, the tools worked, and the model still returned prose where you needed JSON. Control flow above this cannot fix it. Three approaches, differing in when they act.

BAML fixes it at the boundary. Every prompt becomes a function with a typed input and return value, written in a small language that compiles into client code. It optimises nothing and judges nothing, which makes it the cheapest to adopt.

Mellea fixes it at runtime. Built at IBM Research, it lets you attach requirements to a generation. They go into the prompt, then get checked afterwards, and anything failing is retried with the reason attached. Use it for constraints you can check but not score: tone, policy, whether a claim is supported by its source.

DSPy fixes it before runtime. You declare inputs and outputs, write a function that scores an answer, and hand it examples. An optimizer rewrites the instructions until the score goes up. The entry fee is that scoring function, and writing it is usually the real project.

They combine: BAML for the shape, Mellea for the constraints, DSPy for the accuracy. Ax carries DSPy to TypeScript. LangChain used to belong here, but since 1.0 it is an agent API on the LangGraph runtime, which makes it an orchestration framework.

Orchestration frameworks

These give you the loop: control flow, state, and what happens when a step fails. They do not give you tools. That is the sharp line between this category and the next. LangGraph ships nothing that can touch your filesystem; Strands ships nothing that can run a shell command. Every capability is one you wrote, which is right when your tools are three calls into your own API and wrong when the agent must work in a repository.

Two forks live inside this category. The first: either your code decides the next step, or the model does. AWS Strands is the clearest model-driven statement, where the model decides whether to call a tool, keep reasoning, or answer. LangGraph states the opposite, with nodes, edges, explicit state and checkpoints. CrewAI ships both, Crews where agents work out who goes next and Flows where you pin the order down. This is not taste: if you can draw the flowchart, write the flowchart. Model-driven control costs more tokens and latency, and makes it much harder to work out afterwards why the agent did what it did.

The second fork: what does it cost you when a run dies halfway? If the answer is "nothing, we rerun it," retries are fine. If the run takes an hour or waits on a human approval, it has to survive a crash and resume, which means saving progress outside the process. LangGraph does that with checkpoints. Pydantic AI runs agents on Temporal, DBOS, Prefect or Restate, engines that already run long business processes and record every completed step. That is what I would look at hardest for anything long-running.

Language is the next filter, and it deletes most of the list. Nearly all of it is Python; TypeScript has Mastra and the Vercel AI SDK; Rust has Rig. Google ADK spans four languages but is also the front door to Google's runtime, so adopting it quietly picks that too.

Prebuilt harnesses

The word needs pinning down. "Harness" generally means everything around the model, so by that definition every orchestration framework is one. This category is narrower: a harness somebody already built, that you run from your own code. It arrives able to act in a real environment, reading and writing files, running shell commands, working inside a sandbox, and speaking the Model Context Protocol (MCP) to whatever else you connect. It brings what keeps a long session alive too: permission gates, session resume, and summarising the conversation once it outgrows the context window.

Where the previous category hands you the loop empty, this one hands it full. You are driving an agent, not building one, usually as a subprocess on your own machine. What you give up is the inside: the tools, the system prompt and the context strategy are theirs. You keep the task, the permissions, and whatever hooks they expose.

Most of the others are the same bargain from a different vendor. Three are not:

  • pi is the one to read rather than adopt: a small system prompt and four tools make it legible.
  • deepagents packages the pattern as a library, so you can run it against any model.
  • Managed Agents is the category as a service. Anthropic runs the loop and the sandbox; everything else here runs on your machine.

I have paid what this category charges. Building a generative UI agent for IBM Think 2026, I needed a coding agent to go from a visitor's idea to a running app inside two minutes, live. The agent was Bob, IBM's, and it had no SDK, so the integration point was bob -p "your prompt" as a subprocess. It supplied the model and the tools; I supplied the task and a deterministic build step around it. The full build is here.

You inherit two things: opinions you did not choose, and a product roadmap. Google retired Gemini CLI in May 2026 and stopped serving requests on 18 June. That is a fast cycle to be downstream of.

Enterprise agent platforms

Platforms orchestrate too, so capability would put them on top of the previous category rather than beside it. What makes them a different purchase is the perimeter wrapped around the orchestration: which identity an agent acted under, credentials handed over without handing over secrets, what it may touch, what it did, and where memory, evaluation and deployment live. What you do not buy is better reasoning.

The split inside the category matters more than the brand. Business-user surfaces let a domain expert compose the agent: IBM watsonx Orchestrate pairs drag-and-drop with a developer kit underneath, and Copilot Studio and Agentforce 360 hold the same position over their own data. Developer runtimes assume you wrote the agent and need somewhere accountable to run it: Bedrock AgentCore offers runtime, memory, gateway, identity and monitoring as separate services, and does not care which framework wrote the agent. You need this category when the sentences blocking your launch start with "who approved," "who can see," or "what happens when it is wrong."

Which one do you need?

Reaching for the wrong kind fails predictably. Answer an unreliable extraction step with a second agent that double-checks the first, and you have added another unreliable generation plus the job of coordinating the pair. A second pass only helps when the checker looks for something the first step did not.

Combinations worth running

One kind alone is the common case: a classification service is a generation-level tool and your own code, and a CI job that fixes failing tests is a harness in a shell script, because the harness already owns the loop.

Two pairings earn a second dependency. Orchestration plus generation-level, when the run has known steps but one must be accurate: a document pipeline whose extraction step is a DSPy program. Orchestration plus a harness, when repo work is one step of something larger: a migration across two hundred services needs a queue, restart survival and an approval gate, while reading each repository is harness work invoked per service. Do not invert that one. An orchestrator inside a harness loop, supervising an agent already supervising itself, buys overhead and nothing else.

So should you write your own?

Write those forty lines yourself the first time. It is a day of work, and afterwards none of the frameworks look like magic. What it does not buy is production readiness, and the trap is durability: a hand-rolled way of saving progress is often worse than none, because it looks like it works until the process dies at the wrong moment.

Keep it hand-written for as long as four things stay true. The output is easy to check. The path is a fixed sequence you can draw. Your tools are a handful of calls into your own API. Nobody outside your team has to approve what it does. Each of those four going false points at one of the four categories, in that order. You are noticing which responsibility you no longer want.

You will still get one of these wrong. Three protocols now cover the points where the kinds meet: MCP for how an agent reaches a tool, A2A for how one agent calls another across a vendor boundary, and ACP for how an editor talks to a coding agent. Pick tools that speak them and a wrong choice stays a swap.

The framework names on this page will churn. Two of them changed identity while I was writing it. What you can hand over will not.
