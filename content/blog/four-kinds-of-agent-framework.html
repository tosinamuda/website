When an LLM-based agent becomes part of your architecture, two questions follow: Which framework should you use? And do you need a framework at all?

Ask around and you will hear DSPy, LangGraph, the Claude Agent SDK, Amazon Bedrock AgentCore. Those four belong to different categories and take over different parts of the work. Knowing which is which lets you pick one, combine two, or decide a small custom implementation is enough.

Start with their common reference point. At its simplest, a tool-using agent is a model running inside a loop. The loop calls the model, runs whatever tool it requests, adds the result, and goes round again. It stops when the task is done or the budget runs out. A tool is any callable capability exposed to the model: your own function, a hosted service, an MCP server, another agent.

Written out, the whole thing is this:

def run(task: str, tools: dict) -> str:
    messages = [{"role": "user", "content": task}]

    for _ in range(MAX_STEPS):
        reply = client.chat.completions.create(
            model="gpt-5",
            messages=messages,
            tools=[schema(t) for t in tools.values()],
        ).choices[0].message
        messages.append(reply)

        if not reply.tool_calls:
            # Nothing left to do.
            return reply.content

        for call in reply.tool_calls:
            # Run the tool it asked for.
            args = json.loads(call.function.arguments)
            tool = tools[call.function.name]
            messages.append({
                "role": "tool",
                "tool_call_id": call.id,
                "content": str(tool(**args)),
            })

    raise RuntimeError("step budget exhausted")

That fits on one screen, though streaming, retries and real error handling expand it quickly. Three of the categories below take a different part of it away from you, and the fourth wraps the whole thing: which part you keep, and which part you hand over.

These are not layers in a fixed stack. Each names the responsibility a tool mainly takes over, and one system can use several at once.

Feature lists will not tell you which category you need, because these tools overlap and often compose. What sorts them is the responsibility you stop carrying: two tools compete only if you would hand them the same one. DSPy against Mellea is worth comparing. DSPy against LangGraph is a category error.

Generation-level tools

These tools turn a hand-rolled model call into a declared interface. You keep the program and say what a good answer looks like. Each takes over some combination of prompt construction, parsing, validation, repair and optimization, and not all of it at runtime.

The failure sits inside a generation step. The model may return the wrong structure, break a requirement you can validate, or vary in quality across examples. More orchestration will not repair the generation itself.

Three approaches, separated by when they act. BAML acts at the boundary, and is a language rather than a framework: you write the prompt inside a typed function that compiles to a client. Mellea acts at runtime, retrying whatever fails a requirement you attached. DSPy acts before deployment, searching with examples and a metric for better instructions, better demonstrations, or both.

BAML, Mellea and DSPy combine, and the cost usually rises in that order. Declaring a type is often straightforward, a reliable validator takes more work, and a scoring function can become a project of its own.

In code, the loop does not move. One tool inside it stops carrying a prompt:

class ExtractInvoice(dspy.Signature):
    """Read an invoice and return what is payable."""

    document: str = dspy.InputField()
    amount: float = dspy.OutputField()
    due_date: str = dspy.OutputField()

extract = dspy.ChainOfThought(ExtractInvoice)

No formatting instructions, no parsing code. The docstring becomes the instruction DSPy sends, and the field types say what to coerce the result into. Wrap extract in a function and run() calls it like any other tool. The full mechanics are their own subject.

Orchestration frameworks

Orchestration frameworks give you the loop: control flow, state, and what happens when a step fails. What they do not hand you is an assembled environment. Some ship hosted tools, but you still wire up what your application needs. That is the right trade when your tools are a few calls into your own API. It is the wrong one when the agent must work in a repository.

Two forks decide which one you want. Either your code picks the next step, or the model does. Strands starts model-driven, LangGraph from a state graph that can hold both, CrewAI from autonomous Crews beside structured Flows. If you can draw the flowchart, write the flowchart. Letting the model decide costs tokens and latency, and hides why the agent did what it did.

What does it cost you when a run dies halfway? If the answer is "nothing, we rerun it," retries are fine. If the run takes an hour or waits on an approval, it has to save progress outside the process. That means checkpointing, or a real workflow engine underneath, the route Pydantic AI takes.

In code, the for loop and the message list are gone. You declare the steps and the framework runs them:

graph = StateGraph(State)
graph.add_node(fetch_policy)
graph.add_node(draft_reply)
graph.add_edge(START, "fetch_policy")
graph.add_edge("fetch_policy", "draft_reply")
graph.add_edge("draft_reply", END)

config = {"configurable": {"thread_id": "42"}}
app = graph.compile(checkpointer=InMemorySaver())
app.invoke({"ticket": ticket}, config)

fetch_policy and draft_reply are still your functions, and their tools are still yours to write. What you handed over is range(MAX_STEPS), the growing messages list, and what happens when step two dies. Swap the saver for a database and the run resumes on the same thread_id.

Prebuilt harnesses

Used loosely, "harness" means everything around the model, which would make every orchestration framework one. This category is narrower: a prebuilt harness that you invoke from your own code. Where the previous kind hands you the loop empty, this one hands it full. It arrives with file access, a shell, a sandbox and the permission gates that keep a long run alive.

You are driving an agent, not building one. That is the bargain: you inherit its tools, system prompt, and context strategy. Most of it can be extended or overridden, but you did not write it and you do not maintain it. You keep the task, the permissions, and whatever hooks it exposes.

In code there is no loop left to see, and no tools dictionary either:

options = ClaudeAgentOptions(
    allowed_tools=["Read", "Edit", "Bash"],
    permission_mode="acceptEdits",
    cwd="/srv/checkout",
)

task = "Add the new argument to every render_legacy call."

async for message in query(prompt=task, options=options):
    print(message)

Compare that with the first snippet. You wrote neither the tools that read and edit files nor the system prompt choosing between them. Yours are the sentence, the three permitted tools, and the directory.

Harnesses look alike from outside, and the model you already pay for narrows the list. They differ underneath in sandboxing, permissions, which tools ship, and how much you can replace. The coding agent pi is small enough to read rather than adopt.

I have paid what that bargain costs. Building a generative UI agent for IBM Think 2026, I needed a visitor's idea running as an app in two minutes, live. Bob, IBM's coding agent, had no SDK, so I drove bob -p "your prompt" as a subprocess. It supplied the model and the tools; I supplied the task. The full build is here.

You also inherit somebody else's product roadmap. Google retired Gemini CLI in May 2026 and stopped serving requests on 18 June. That is a fast cycle to be downstream of.

Enterprise agent platforms

What you buy here is the perimeter around the orchestration: which identity the agent acts under, what it may access, what it did, and where it runs. Better reasoning is not what this category sells. Platforms do orchestrate, which is why capability alone would stack them on the previous kind rather than set them beside it.

The split inside the category matters more than the brand. Business-user surfaces let a domain expert compose the agent, wired into a vendor's own data. Developer runtimes assume you wrote it already and need somewhere accountable to run it.

You need this kind when the sentences blocking your launch start with "who approved," "who can see," or "what happens when it is wrong." Managed deployment, data residency and governance can bring you here first.

Which one do you need?

Reaching for the wrong kind fails predictably. Check an unreliable extraction step with a second agent at runtime, and you have two unreliable generations to coordinate. Start with the provider's structured output or a validator, then score the step offline. Add runtime checks only when they are independent.

A prototype usually needs one kind. Production systems combine several, and each addition should answer a failure you have seen. The pairing I reach for is orchestration plus a generation-level tool: known steps, one of which must be accurate.

Should you write your own?

Write that loop yourself the first time. It is small enough to build as an exercise, and afterwards no framework looks like magic. What it does not buy is durability: a hand-rolled way of saving progress is often worse than none, because it looks like it works until the process dies.

Keep it hand-written while four things stay true. The output contract is simple enough to enforce yourself. The path is a fixed sequence you can draw. Your tools are a few calls into your own API. Nobody outside your team approves what it does. Whichever stops being true names what to hand over next.

That leaves the two questions you arrived with. Which framework? Start with the category matching the responsibility your system can no longer carry. Compare inside it on ecosystem fit, extensibility, operational maturity and exit cost. Should you write your own? Yes, once, and keep it until one of those four conditions goes false.

The names on this page will churn, and two were renamed while I was writing it. The responsibilities move far more slowly.
