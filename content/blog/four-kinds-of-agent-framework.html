Agent tools differ most in the part of the system they supply. Some help you define and improve one model-driven operation, such as routing a support ticket. Others run a sequence of steps or agents. A prebuilt harness can already work in a repository, shell, or browser. A platform adds the controls needed to operate agents in production.

Each ready-made part also brings its own design choices. Ask what you want ready-made, which behaviour must remain under your control, and whether the extension points fit your application.

I group the choices into generation programming tools, orchestration frameworks, prebuilt agent harnesses, and enterprise agent platforms. Building the agent yourself is the fifth option.

These labels describe how you adopt a product in one system. A product can cross boundaries when you use it in different ways. The names in this essay are examples; the list is intentionally incomplete.

Features overlap, so a checklist will not classify the tool. A generation program can contain a small agent loop. An orchestrator can include memory or a default agent. A harness can coordinate subagents. Classify the part you ask the tool to own in your system.

The short Python sketches below show that boundary. The generation and orchestration examples use real libraries. The others use generic interfaces.

Building your own

Without an agent framework, you start with the model client and any tool-calling primitives you choose. You write the loop and decide how every tool call works.

while True:
    reply = model(
        messages,
        tools=tools,
    )
    if not reply.tool_calls:
        return reply.text
    results = run_tools(
        reply.tool_calls
    )
    messages += results

This sketch leaves out stop conditions, persistence, memory, context compaction, permissions, and observability. Those decisions remain visible and changeable because they remain in your code. Their design, testing, operation, and upgrades also belong to you.

Build the agent yourself when you need full control and a framework would constrain an important choice. The system can be simple or complex. Complexity sets the engineering cost; the need for control sets the choice.

Generation programming tools

I use generation programming for one model-driven operation inside a larger program. Suppose a support system must decide whether a ticket is urgent. The ticket goes in; one true or false answer must come out.

triage = dspy.Predict("ticket -> urgent: bool")

def triage_accuracy(example, prediction, trace=None):
    return prediction.urgent == example.urgent

score = dspy.Evaluate(
    devset=labelled_tickets,
    metric=triage_accuracy,
)(triage)

A generation programming tool makes that operation manageable. You control its prompt, input, output, examples, requirements, and quality measure. You can then test, optimise, or repair it. The implementation can make more than one model call or run a small agent loop. It still owns one defined job: judging urgency.

You decide when triage runs and what happens to its answer. You also supply any domain tools, memory, session state, and context policy used by the wider application.

Choose this boundary when you can split the work into model-driven operations that you can test separately. Consider a document pipeline that always loads, extracts, and stores an invoice. Malformed output points to the extraction operation. Changing the workflow will not make that output valid.

DSPy uses signatures and modules to define programs, then metrics and optimisers to improve them. Mellea attaches requirements to a generation, checks the result at runtime, and can repair a failure.

Orchestration frameworks

An orchestration framework runs a sequence of steps or agents. It supplies the loop or graph. Depending on the framework, it also handles routing, shared state, retries, checkpoints, and approval.

builder = StateGraph(Run)
builder.add_node("triage", triage_step)
builder.add_node("patch", coding_agent)
builder.add_node("deploy", deploy)
builder.add_edge(START, "triage")
builder.add_edge("triage", "patch")
builder.add_edge("patch", "deploy")

app = builder.compile(
    checkpointer=InMemorySaver(),
    interrupt_before=["deploy"],
)

You provide the three step functions, and triage_step wraps the program from the previous section. The framework connects the steps, carries state between them, saves a checkpoint at each one, and holds the run before deployment until a person approves. You choose the models, tools, agents, control flow, and context policy. Some frameworks also supply memory or default tools.

Choose orchestration when coordination is the hard part. This includes multi-step runs, work that must survive interruption, and flows that mix fixed code with model decisions. A generation program or agent harness can become one callable step in that run.

LangGraph, Strands, Google ADK, CrewAI, and Pydantic AI offer different balances between explicit workflows and model-directed agents.

Prebuilt agent harnesses

A prebuilt harness gives you a working agent. The model connection, loop, standard tools, permissions, sessions, and context handling are already wired together. A coding harness can often inspect a repository, edit files, and run commands on its first task.

task = (
    "Fix issue #418. "
    "Run tests and show the diff."
)
result = coding_agent.run(task)

You supply the task, access, and extensions. Instructions, skills, hooks, custom functions, and MCP servers let you adapt the agent. You work through the extension points the harness exposes.

Choose a harness when the job depends on acting in an environment and you want that capability ready-made. The Claude Agent SDK, Codex SDK, OpenCode, and deepagents expose working agents through libraries, command-line interfaces, or servers.

Enterprise agent platforms

An enterprise agent platform supplies the managed environment around an agent. It may provide hosting, identity, access control, secrets, security enforcement, audit trails, observability, evaluation, and deployment.

platform.deploy(
    coding_agent,
    identity="repo-agent",
    policy=repository_policy,
    audit=True,
)

You still define the agent's behaviour, business tools, and policies. The platform gives those choices an accountable place to run. It can host an orchestrated agent, expose a harness as a service, or connect to a component through an API or MCP server.

Choose a platform when governance, security, observability, or managed cloud operation determines whether the agent can ship. Bedrock AgentCore accepts agents built with different frameworks and models. IBM watsonx Orchestrate, Copilot Studio, and Agentforce provide agent-building surfaces around enterprise data and controls.

How the categories compose

Different categories are not alternatives, and they are not a stack either. Each boundary can expose a callable interface: a function, a tool, an API, a command-line program, or an MCP server. Once it does, any kind can sit inside any other.

Orchestration registers a generation program as a tool, or invokes a harness as one step of a run. A harness runs a generation program as a skill, as a script, or over MCP. A generation program calls a harness as one of its tools, or uses one as the layer that acts. Those last two are the same pair pointing opposite ways, which is why there is no fixed order to draw. A platform is the exception, because it wraps whatever runs rather than waiting to be called.

Framework names and feature lists will change. Adopt a boundary when its ready-made functionality is worth the responsibility you hand over.
