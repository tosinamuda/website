A container is a packaged copy of your app and everything it needs to run, so it behaves the same on your laptop as it does on a server. To put a React app in one, you write a Dockerfile: a list of steps Docker follows to produce an image, which it then runs as a container.

The catch with React is that there is no single right Dockerfile, because there is no single kind of React app anymore. Which Dockerfile you need comes down to one question: does any of your React run on the server at request time?

  • No — a plain client-rendered app. You build it into static files and serve them with a web server like Nginx. There is no Node in the running container.
  • Yes — some of your React runs on the server, the way server-side rendering and React Server Components do. Something has to execute JavaScript on every request, so the running container is a Node process.

Every React container does the same three things

However it renders, a React container does three things, in order:

  1. Install dependencies — npm ci (like npm install, but it installs exactly what package-lock.json pins, which is what you want in a repeatable build)
  2. Build the app — npm run build
  3. Run it — npm start, or node server.js, or a static file server like serve or Nginx

The first two steps are identical for every React app. The third is the one that changes, and it is what the rest of this post is really about: a client-only app just needs something to hand over static files, while a server-rendered app needs a live Node process. Same install, same build, different run.

One more idea makes the Dockerfiles readable: a Dockerfile can have more than one stage, each starting with its own FROM line. Earlier stages build things; the last stage is the image you actually ship and run. Anything in an earlier stage is thrown away unless you explicitly copy it forward — that is what keeps the final image small, and it is the difference between the two cases below.

What "runs on the server" actually means

Step 3 splits on one thing: does your app build its HTML by running code on the server for each request, or does it just ship files that the browser fills in? Two React features put work on the server, and the difference is worth seeing plainly:

  • Server-side rendering (SSR) builds the page's HTML on the server for each request and sends that to the browser, which then hydrates it into an interactive app. The component code still ships to the browser too.
  • React Server Components (RSC) go further: some components run only on the server, and their code never reaches the browser at all.

The mechanics differ, but for containerizing they mean the same thing: a JavaScript runtime has to be running when a request comes in. That is the line. If any rendering happens per request, step 3 is a Node process; if not, it is a static file server.

Client-only: build static files, serve with Nginx

For a client-rendered app — a plain Vite or Create React App SPA — the build output is just a folder of static files (dist/ with Vite, build/ with CRA). The simplest possible Dockerfile builds and serves from one image:

FROM node:22-alpine
WORKDIR /app
COPY . .
RUN npm ci && npm run build
RUN npm install -g serve
EXPOSE 3000
CMD ["serve", "-s", "dist"]

This works, but the final image drags along Node, every dependency, and your source — none of which a browser-served app needs. This is exactly what a second stage fixes: build in a Node stage, then copy only the finished static files into a tiny Nginx image and discard the toolchain.

FROM node:22-alpine AS builder
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build          # Vite writes to /app/dist

FROM nginxinc/nginx-unprivileged:alpine
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=builder /app/dist /usr/share/nginx/html
EXPOSE 8080

The one config a single-page app needs is a fallback to index.html, so client-side routes resolve instead of returning 404:

server {
    listen 8080;
    location / {
        root /usr/share/nginx/html;
        try_files $uri /index.html;
    }
}

The final image now holds HTML, CSS, JS, and Nginx — no Node, no node_modules, no source.

Ports: how your browser reaches the container

Notice the EXPOSE 8080 in that Dockerfile. Ports are where first-time containerizing usually goes wrong, so it is worth slowing down on.

Inside the container, the web server listens on a port — 8080 for the Nginx image above. That port lives inside the container. By default, nothing on your machine can reach it.

Two flags do two different jobs, and confusing them is the usual stumbling block:

  • EXPOSE 8080 in the Dockerfile is documentation. It records which port the app listens on. It does not, on its own, make the port reachable from your machine.
  • docker run -p 8080:8080 is what actually publishes the port. The format is -p HOST:CONTAINER: the left number is the port on your machine, the right number is the port inside the container.

So to build and run the static image:

docker build -t my-react-app .
docker run -p 8080:8080 my-react-app

Now open http://localhost:8080. Your browser always talks to the host port — the left number. The two numbers do not have to match: -p 3000:8080 would serve the container's 8080 on your machine's 3000 instead, and you would visit http://localhost:3000.

One question this raises: why 8080 and not 80? The nginx-unprivileged image runs as a non-root user, and non-root users cannot bind ports below 1024, so it listens on 8080. A Node server, in the next section, conventionally listens on 3000.

Server-rendered: run a Node process

For SSR or RSC, the final image runs Node. The simplest version is again a single stage — install, build, start:

FROM node:22-alpine
WORKDIR /app
COPY . .
RUN npm ci
RUN npm run build
ENV NODE_ENV=production
EXPOSE 3000
CMD ["npm", "run", "start"]

It runs, but it ships your dev dependencies and source into production. The multi-stage version builds in one stage, then installs only production dependencies in a clean runtime stage and copies the build output across:

FROM node:22-alpine AS builder
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:22-alpine AS runner
WORKDIR /app
ENV NODE_ENV=production
COPY package.json package-lock.json ./
RUN npm ci --omit=dev                      # production deps only
COPY --from=builder /app/build ./build     # output path varies by framework
USER node
EXPOSE 3000
CMD ["npm", "run", "start"]

Same idea as before — the container listens on a port (3000 here), and you publish it when you run:

docker build -t my-react-app .
docker run -p 3000:3000 my-react-app

The build output directory and start command above are placeholders — they depend on the framework, which is the next section. One caveat first: a Node container is not the only way to run server React. Most SSR frameworks can also target edge or serverless runtimes, where there is no long-lived server and no container at all. If you are containerizing, a long-running Node process is the right model — just know it is one of several targets.

By framework

That split — static files or a Node process — is the whole idea. Per framework, it just comes down to knowing which build mode gives you static output and which gives you a server, so here is each one as a client image beside a server image.

Next.js

Next.js renders on the server by default. Set output: 'standalone' and the build emits a self-contained .next/standalone folder with only the dependencies it actually uses, started by a generated server.js. Set output: 'export' instead and you get a fully static site — back to Nginx.

Client · output: 'export'
FROM node:22-alpine AS builder
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build      # writes /app/out

FROM nginxinc/nginx-unprivileged:alpine
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=builder /app/out /usr/share/nginx/html
EXPOSE 8080
Server · output: 'standalone'
FROM node:22-alpine AS builder
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:22-alpine AS runner
WORKDIR /app
ENV NODE_ENV=production
COPY --from=builder /app/.next/standalone ./
COPY --from=builder /app/.next/static ./.next/static
COPY --from=builder /app/public ./public
USER node
EXPOSE 3000
CMD ["node", "server.js"]

Vite

Plain Vite is a client SPA: vite build writes static files to dist/. Adding SSR (Vite's SSR mode, or a framework built on Vite) gives you a server entry you run with Node.

Client · SPA
FROM node:22-alpine AS builder
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build      # writes /app/dist

FROM nginxinc/nginx-unprivileged:alpine
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=builder /app/dist /usr/share/nginx/html
EXPOSE 8080
Server · SSR
FROM node:22-alpine AS builder
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build      # client + server bundles

FROM node:22-alpine AS runner
WORKDIR /app
ENV NODE_ENV=production
COPY package.json package-lock.json ./
RUN npm ci --omit=dev
COPY --from=builder /app/dist ./dist
USER node
EXPOSE 3000
CMD ["node", "server.js"]

React Router v7 (formerly Remix)

React Router's framework mode is server-rendered: the build splits into build/server and build/client, run with react-router-serve. Opt into SPA mode and it builds to static files in build/client instead.

Client · SPA mode
FROM node:22-alpine AS builder
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build      # ssr:false → static

FROM nginxinc/nginx-unprivileged:alpine
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=builder /app/build/client /usr/share/nginx/html
EXPOSE 8080
Server · framework mode
FROM node:22-alpine AS builder
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:22-alpine AS runner
WORKDIR /app
ENV NODE_ENV=production
COPY package.json package-lock.json ./
RUN npm ci --omit=dev
COPY --from=builder /app/build ./build
USER node
EXPOSE 3000
CMD ["npm", "run", "start"]   # react-router-serve

TanStack Start

TanStack Start is SSR-first and built on Vite. The build emits a Node server entry you start with node; it can also prerender or run in SPA mode for a fully static output. The exact output path and start command track the version and deployment preset, so confirm those rather than copying a path blindly — but the two shapes are the same as everywhere else.

Client · prerender / SPA
FROM node:22-alpine AS builder
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build      # static client output

FROM nginxinc/nginx-unprivileged:alpine
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=builder /app/dist /usr/share/nginx/html
EXPOSE 8080
Server · SSR
FROM node:22-alpine AS builder
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build      # server entry

FROM node:22-alpine AS runner
WORKDIR /app
ENV NODE_ENV=production
COPY package.json package-lock.json ./
RUN npm ci --omit=dev
COPY --from=builder /app/.output ./.output
USER node
EXPOSE 3000
CMD ["node", ".output/server/index.mjs"]

The one rule to carry away

Before you write the final stage of a React Dockerfile, ask whether anything renders at request time. If nothing does, ship static files behind a file server and keep Node out of production. If something does, ship a Node process and give it only the build output and production dependencies. Either way, the container listens on a port, and -p HOST:CONTAINER is what hands that port to your browser. The first two steps are always the same; the rendering model decides the last one.
